# 094｜照原樣公布

第三十二日下午一點四十二分，資料局的公開技術變更單進了第六修復室。

不是案件通知。

也不是歷史完整性端送來的新結果。

只是舊格式解析器上午那批修正，依維護規則要補一份公開相容性公告。

任何會改變外部單位「舊封套應如何被讀回」的 parser 行為，都不能只留在內部修復紀錄裡。

第三組較資淺修復員正在處理自己的新來源，沒有抬頭。

林澈先把公告打開。

草稿很短。

【Legacy parser compatibility update】

【affected field：legacy subject anchor】

【compatibility family：MUNI-LEGACY/INGEST】

【new behavior：preserve opaque legacy value】

【automatic remap to current subject identifier：disabled】

最下面有一個黃色標記。

【publication wording review required】

主管也看到了。

「不是叫你決定要不要公開。」她先說。

「我知道。」

「你只看技術用語有沒有把已知事實寫錯。」

「好。」

公開技術文件編輯席已經在草稿旁留了一段建議。

【為非技術讀者，可將 legacy subject anchor 簡化為：舊身份識別鍵】

林澈看到那行，手停了下來。

主管問：「哪裡有問題？」

「『身份識別鍵』太多。」

「說清楚。」

林澈把 2163 介面契約的公開欄位定義拉到旁邊。

沒有任何案件值。

沒有那兩個 source roots。

只有 generic field rule。

「我們現在知道這個欄位在 handoff 層是 opaque carry。」他說，「也知道本地沒有 semantic interpretation 跟 merge authority。」

主管點頭。

「所以？」

「把它翻成『身份識別鍵』，會讓讀者以為我們已經知道它是在識別一個人。」

「你覺得不是？」

「我不知道。」

林澈說完，自己先看了一眼那句話。

這一次，「不知道」不是把內容留在黑箱裡的理由。

反而是公開文件不能替未知補語意的理由。

他在文字審查欄填上：

【建議：保留原 field class 名稱；補充「opaque legacy field，無現行 semantic mapping」。不翻譯為 identity key。】

主管沒有替他改。

「可以。」

公開技術文件編輯席很快回覆。

【接受。】

接著又出現第二個問題。

【`MUNI-LEGACY/INGEST` 是否因涉及 active historical-integrity matter 而暫緩公開？】

這次林澈沒有碰鍵盤。

主管也沒有。

因為這不是技術措辭問題。

系統自動把問題轉到資訊公開審核端。

等待不到七分鐘，結果回來。

【temporary publication hold：NO】

【理由：generic namespace 與 interface contract 為既存 public technical registry material】

【case-specific subject values：not included】

【case-specific anchor value：not included】

【historical-continuity relation：not disclosed】

【publication impact：generic parser compatibility only】

林澈讀到最後一行。

一個很短的念頭冒出來。

如果暫緩呢？

至少外面的人不會因為這次 parser 更新，再看見 `MUNI-LEGACY/INGEST` 這個名字。

不會有人順手搜尋它。

不會有人把 `legacy subject anchor` 和那個舊 namespace 放在同一頁上。

這些都是真的。

可另一件事也是真的。

那份介面契約本來就是公開技術見證。

namespace 不是因為他的案件才存在。

field class 也不是。

如果現在只因為林澈終於知道它們可能和自己的歷史問題有關，就把原本可公開的 generic 技術資訊藏起來，那不是保護案件。

那是讓案件開始改變別人本來有權知道的東西。

主管看了他一眼。

「想申請再覆核？」

林澈搖頭。

「沒有新的理由。」

「怕人看見不算？」

「不算。」

主管把結果簽收。

---

兩點二十三分，公開公告進入發布前預覽。

這次文字更短。

【舊格式解析器相容性更新】

【受影響欄位：`legacy subject anchor`】

【相容家族：`MUNI-LEGACY/INGEST`】

【處理規則：驗證欄位類型與簽章封套後，以 opaque legacy field 原樣保留】

【不進行：自動映射為現行 subject identifier／本地語意解讀／subject merge】

【本公告不包含任何 subject value 或人物資料】

林澈從頭看到尾。

沒有他的名字。

沒有 A-2162-02。

沒有那個 specific anchor。

沒有「兩端共享同一值」。

也沒有歷史案件。

只有一條已經能站得住的 generic 技術事實。

較資淺的修復員這時才轉過來。

「你們在看什麼？」

「昨天 parser 修正的公開公告。」主管說。

她把預覽拉到自己螢幕邊緣。

「喔。」

看完前三行，她停了一下。

「這個現在可以公開？」

主管反問：「哪個不能？」

「那個 MUNI。」

「它本來就是 public technical registry material。」

「可是現在不是跟林澈那件事有一條關係？」

林澈說：「generic schema relation。」

「我知道。」

她盯著公告。

「所以公開這個，不會把你的那個也公開？」

「不會。」

「那如果有人自己看懂？」

林澈沒有立刻回答。

因為這個問題跟「有人看見」不是同一件事。

公開資料被理解，本來就是公開的其中一部分。

真正需要保護的是不該被公開的 case-specific value、人物資料與受控 relation。

不是保證所有外部讀者都永遠無法把公開事實放在一起思考。

主管先說：「如果公開材料本身足以支持一個結論，那個結論就不屬於我們可以靠藏公告阻止的東西。」

較資淺的修復員看向林澈。

「你聽起來會不舒服。」

「會。」

「那還發？」

「公告不是我的。」

她皺眉。

林澈補了一句。

「我是說，它不是因為我的案件才有權存在。」

她這才懂。

「喔。」

她把預覽縮回去。

「那就發啊。」

主管說：「也不是妳決定。」

「我知道。」

「妳剛剛語氣很像。」

「我只是提供民意。」

林澈笑了一下。

三點整，公告正式發布。

沒有警報。

沒有新聞推送。

也沒有任何人立刻打電話到資料局問「legacy subject anchor 到底是誰」。

公開技術頁面只是多了一筆版本紀錄。

版本號。

生效時間。

回退方式。

簽章。

以及那幾行很容易讓大多數人直接略過的相容性說明。

林澈重新打開一次。

不是為了確認有沒有人看。

只是確認發布版沒有把 `opaque legacy field` 改成「身份識別鍵」。

沒有。

他關掉頁面。

---

下午四點多，公開技術支援佇列真的進了一個問題。

不是記者。

不是研究者。

也不是任何認得林澈的人。

是一個外區舊檔案整合單位的格式維護員。

【請確認：遇 `legacy subject anchor` 時，是否應轉換為現行 person／subject id 以利 downstream indexing？】

問題被分派到 parser 維護組，不在林澈工作列。

他只是在公共支援頁面上看見了。

回覆很快。

【否。】

【該 field 為 opaque legacy field。可驗證 class／signature envelope，應原樣攜帶；無現行 semantic mapping 時不得自行轉換為 person／subject identifier。】

【若 downstream 業務需要人物識別，應由該業務自身合法 identity process 建立，不得由 compatibility field 推導。】

林澈看完。

這不是新的案件證據。

甚至不是新的制度事實。

只是原本已建立的規則，被一個完全不知道他存在的人，在完全不同的地方問了一遍。

而答案仍然一樣。

不能因為欄位看起來像身份，就替它決定身份。

公開也沒有讓它更像答案。

只讓那條界線不再只存在於他們的內部畫面上。

五點十二分，林澈準備下班。

historical-continuity passive route 一整個下午都沒有新通知。

specific anchor 的 origin 沒有因此浮出來。

B-17 沒有因此變成 carrier。

也沒有任何外部人因為讀到公開公告，就突然替他把缺的那一層歷史補完。

公開的只是能公開的部分。

未知仍然是未知。

林澈關掉工作站。

這次他沒有因為一個名字出現在更多人的螢幕上，就覺得它離答案更近。
