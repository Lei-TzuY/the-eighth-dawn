# 092｜三十一份不是我的

第三十一日下午兩點十七分，較資淺的修復員把早上的紅色佇列重新打開。

紅色已經不見了。

三十一份舊制交換封套都能被新版解析器讀回，`legacy subject anchor` 也不再被刪除或硬映射成現行識別欄位。

取而代之的是一個灰色標記。

【retention routing：pending】

她看了兩秒。

「這又是什麼？」

林澈正在核對地下停車區濕度記錄器的電池更換表，沒有立刻轉身。

「看完整。」

她把標記展開。

【原因：generic field class 與 retained historical-continuity question 存在 direct schema relation】

【待定：是否施加 investigative preservation hold】

【範圍：31 legacy envelopes】

房間安靜了一下。

較資淺的修復員說：「所以早上沒開，下午要把它們全留下來？」

林澈把手裡的表格放下。

三十一份封套裡有醫療轉介、教育轉接、災後臨時住所資格、公共照護名冊。

他們早上沒有看任何一個人的名字。

也沒有看任何一個 `legacy subject anchor` 的值。

只知道這些封套曾合法攜帶同一種欄位類別。

而現在，那個欄位類別確實和他的 historical-continuity problem 有了直接格式關係。

這已經足以讓保存系統問下一個問題。

不是能不能讀。

而是該不該因為這個新關係，把本來各自有保存期限的三十一份資料全部暫停到期。

主管從隔壁桌走過來。

「先不要碰 retention routing。」

較資淺的修復員問：「我們本來有權處理嗎？」

「沒有。這是紀錄治理端的問題。」

她看向林澈。

「你也沒有。」

「我知道。」

「你可以提供今天上午 parser fix 需要哪些技術材料。不能替他們決定哪些 subject records 因為你的歷史問題值得延長保存。」

林澈點頭。

這一次，他甚至沒有覺得那句話需要忍耐。

主管把 retention review 轉到獨立紀錄治理端。

不是人物案件。

也不是歷史完整性端單獨決定。

因為問題已經變成另一種：

一個格式欄位忽然對一件調查有了意義，能不能因此改變所有攜帶這個欄位之人的資料保存期限？

十五分鐘後，遠端席位加入。

對方沒有名字，只顯示職務：

【records-purpose reviewer】

第一個問題很普通。

「上午的 parser 修復，如果沒有這三十一份 subject payload，能不能重驗？」

較資淺的修復員看林澈。

林澈沒有接。

這是她的工作。

她把上午的修正包打開。

「可以。修正依據是簽章有效的 2163 generic interface contract、field class 定義、解析器 regression fixture，還有 batch-level parse outcome。人物內容沒有進 regression fixture。」

「需要保留三十一個 anchor value 嗎？」

「不需要。」

「需要保留姓名、地址、醫療、住所或照護內容嗎？」

「不需要。」

「要證明這個欄位在真實封套裡存在過呢？」

她停了一下。

林澈看著她。

她沒有回頭求答案。

「原封套各自的既有來源鏈在原業務保存期內可以證明。技術修正本身只需要保存『有合法 field class 被 parser 錯誤隔離』的批次級見證，不需要把每一份內容複製進新用途。」

遠端席位說：「對。」

較資淺的修復員肩膀鬆了一點。

第二個問題才真正落到林澈身上。

「historical-continuity problem 是否已經需要比較這三十一份 envelope 的 anchor values？」

主管回答。

「沒有。」

「是否已有 specific case anchor value 可供 lawful comparison？」

「沒有。」

「是否已有 direct relation 指向其中任何一份 envelope？」

「沒有。」

「B-17？」

主管說：「沒有 direct anchor relation。」

「市政連續性服務？」

「不是 anchor originator，至少目前沒有證據建立。」

遠端席位停了一秒。

「那就沒有 blanket hold basis。」

較資淺的修復員眨了一下眼。

林澈沒有。

他只是看著三十一個灰色標記。

如果是第一晚，他大概會覺得這個答案太快。

資料明明還在。

而且現在已經知道它們攜帶某種和自己案件直接相關的欄位類別。

既然可能有用，為什麼不先留下？

這個問題他以前問過自己很多次。

只是那時候面前只有一枚即將被清除的晶片。

現在是三十一份屬於別人的生活紀錄。

他甚至沒有資格知道其中誰還活著、誰已搬離、誰曾生過什麼病、誰在災後住過哪裡。

「如果以後真的發現，specific anchor value 需要拿來比對呢？」較資淺的修復員問。

records-purpose reviewer 回答得很平。

「那要從那個未來問題自己的必要性開始。」

「可是到時候可能有資料已經依原期限到期。」

「對。」

她沉默。

「那不是損失嗎？」

這次林澈開口。

「可能是。」

她看他。

「你居然說可能是。」

「如果未來真的有一個合法問題，而某份資料剛好已經到期，那對那個問題來說當然可能是損失。」

「那現在還是不留？」

林澈沒有替 reviewer 回答。

他只說自己能說的部分。

「因為我們今天知道的是欄位類別有關，不是這三十一個人的內容都跟我的問題有關。」

較資淺的修復員看著佇列。

「可是它們都有那個 field。」

「對。」

「都可能有 anchor value。」

「對。」

「還是不能算？」

林澈想了一下。

「格式證據已經成立了。」

他指向那份 2163 介面契約。

「要把三十一份人的資料也留下來，得有另一個理由。」

他沒有說「這不是我的證據」。

那句話太像一句已經準備好的結論。

但他心裡知道，真正的界線就在那裡。

一個人的醫療轉介不會因為欄位名稱碰到他的案件，就變成他的歷史。

一個家庭的臨時住所資格也不會。

如果調查需要的是格式，就保留格式。

如果未來真的需要某個 subject record，就讓那個未來問題自己證明為什麼需要。

不是先把所有人留下，再等答案來挑。

---

三點二十九分，retention review 定案。

【blanket investigative hold：NO】

【generic interface contract：retain under technical registry】

【parser regression fixture：retain】

【batch-level compatibility witness：retain／no subject values】

【individual envelopes：return to originating retention schedules】

【historical-continuity case ingestion：none】

沒有一份封套被複製進林澈的問題包。

也沒有一個 anchor value 被抽出來做新的比較表。

三十一份資料只從解析器的暫時隔離狀態，回到各自原來的保管者與保存期限。

其中有些還會留很多年。

有些可能比較早到期。

林澈不知道是哪一些。

系統也沒有理由告訴他。

較資淺的修復員按下確認前，又看他一眼。

「你不會想記一下 envelope id？」

「做什麼？」

「不知道。」

她自己先笑了。

「好，這個答案很危險。」

「所以不要記。」

她按下確認。

三十一個灰色標記依序消失。

不是被刪除。

不是被銷毀。

只是離開他們的工作佇列，回到原本該去的地方。

最後一份封套退回來源保管域時，畫面上只剩上午的 parser 修正摘要。

【opaque legacy field／validated／carry unchanged】

較資淺的修復員說：「結果我們保留最多的，反而是『不要解讀』這件事。」

林澈看著那行字。

「因為那是今天真的知道的。」

她關掉佇列。

「那你的那個呢？」

「哪個？」

「真正那個 anchor。」

林澈知道她問的是什麼。

「還是不知道。」

「但現在至少知道 MUNI 那條。」

「知道格式怎麼帶。」

「不能往裡面看。」

「不能。」

她嘆氣。

「你這個案子真的很擅長讓人知道門框，然後不給門。」

林澈笑了一下。

「今天連門框都不要亂留別人的名字。」

四點前，他們回到地下停車區濕度紀錄。

這一次，較資淺的修復員自己把新舊感測器編號對完。

林澈只在她送出前看了一眼。

沒有灰色通知。

沒有新的 direct relation。

也沒有哪一份剛剛離開佇列的舊封套突然回來。

三十一份資料仍然存在於它們各自應有的制度裡。

但不再因為他的問題，被迫一起等待他的答案。
